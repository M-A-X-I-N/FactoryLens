# 1. External Call Map feasibility study

Status: **completed**. Migrated from `M-A-X-I-N/satisfactory-wiremod-rss-integration` at source commit `8d0ee54f80a9123142cba13f00a175be1161244f` on 2026-09-24.

This experiment asks whether the existing Satisfactory/Unreal/SML development machinery can support a **project-wide rooted call map** for code-reading and source archaeology.

The desired developer experience is roughly:

```text
external/framework entry point
    ↓
project-local call
    ├─ project-local call
    │  └─ ...
    └─ project-local call
       └─ ...
```

For example, while studying RSS2, a manually confirmed or automatically inferred Unreal/SML callback would be treated as a graph root and ordinary project-local calls would be followed recursively from there.

The experiment deliberately prefers existing machinery over a bespoke parser:

```text
SML Starter Project / UnrealBuildTool
    ↓
real compile configuration / compilation database if available
    ↓
Clang / clangd semantic indexing and call-hierarchy facilities where viable
    ↓
small project-specific root/discovery/traversal layer
    ↓
tree/graph output
```

A Rider tool window is **not** part of the BX feasibility gate. First prove that the semantic data can be obtained and assembled reliably. UI integration only becomes worth discussing after that.

## 1.1 Scope and constraints

The first target is the RSS2 source tree because it is large enough to be meaningful while still being a bounded project/module set.

The experiment should:

- avoid writing a new C++ parser;
- use UnrealBuildTool-generated project knowledge wherever practical;
- prefer Clang/clangd/LLVM semantic information over regex-based source interpretation;
- keep manually declared entry points outside vendored source when possible rather than creating local diffs in RSS2/Wiremod;
- distinguish **confirmed**, **inferred**, and **candidate** roots rather than pretending all heuristics are equally reliable;
- keep generated indexes, compilation databases, logs, and graph output under ignored `work/` state unless a small fixture is intentionally promoted later;
- remain entirely developer-tooling/static-analysis work and therefore outside gameplay implementation.

## 1.2 What counts as "possible"

BX is successful once we can establish that the existing toolchain can provide enough semantic information to:

1. understand representative RSS2 translation units with the real Unreal/SML compile environment;
2. resolve ordinary cross-file project-local call edges;
3. start from at least one explicit entry-point root and recursively produce a useful bounded call tree/graph;
4. identify at least one useful class of entry-point candidate without manually annotating every root;
5. explain the remaining blind spots clearly enough that they look like enrichment work rather than a fundamental blocker.

The goal is **not** to prove perfect reconstruction of every Blueprint/reflection/delegate/hook edge. The goal is to determine whether a useful project-wide map can be built mostly from existing semantic machinery.

## 1.5 B2 method — compare semantic inputs before choosing a backend

**Status: passed on the configured Windows UE 5.6.1-CSS / SML workspace (2026-09-23).**

B2 deliberately does not assume that the first compilation database clangd can consume is the best long-term input.

The primary comparison keeps the target/source files fixed and changes only the compiler view supplied by UnrealBuildTool:

```text
A. FactoryEditor / Win64 / Development
   -Compiler=VisualStudio2022
   -> real Windows build metadata from B1
   -> clangd

B. FactoryEditor / Win64 / Development
   -Compiler=Clang
   -> UBT's Clang-native view of the same workspace
   -> clangd
```

The same representative files are checked under both databases:

```text
RSS2:
Mods/GameFeatures/RSS/Source/RSS/Private/Subsystem/RSSDataManagerSubsystem.cpp

Wiremod:
Mods/FicsitWiremod/Source/FicsitWiremod/Private/Behaviour/Displays/ManagedSign/ManagedSign.cpp
```

These are intentionally non-trivial translation units that pull in Unreal-generated/reflected types plus project and dependency symbols.

Run:

```powershell
python .\playground\external-call-map\b2_compare_clangd_inputs.py
```

The script:

1. reuses the proven B1 MSVC-derived database;
2. asks UBT to generate a second ignored database with `-Compiler=Clang`;
3. runs `clangd --check` against both representative files under both available databases;
4. preserves verbose logs and a compact comparison summary under `work/external-call-map/b2/`.

If the Clang UBT database cannot be generated, that is retained as B2 evidence and the MSVC-database checks still run. If neither input gives a credible semantic result, B2 should pause and compare the same code paths against the call-hierarchy/project understanding already exposed by Rider/ReSharper C++ or Visual Studio before making a backend decision.

### 1.5.1 First comparison result

The first configured Windows run used Visual Studio's bundled clangd 19.1.5 and successfully generated the second UBT database with `-Compiler=Clang`.

```text
Clang view: clang-cl.exe @<Unreal per-TU response file>
```

- Because the source diagnostic is identical under both compiler views, there is currently no evidence that the B1 MSVC-derived database is semantically worse than the Clang-derived database for these translation units.

The comparison helper now reports source diagnostics, tweak failures, and other clangd errors separately so later runs do not conflate `--check` feature-test failures with parser diagnostics.

### 1.5.2 B2 conclusion

B2 passes.

For B2 foreground semantic-resolution work, the default stack is:

```text
UBT
  -> FactoryEditor / Win64 / Development
  -> -Compiler=VisualStudio2022
  -> real B1 compile_commands.json
  -> clangd
```

This B2 preference is specifically about foreground symbol resolution. B3 later established that call-hierarchy behavior is version/input-sensitive; use the B3 conclusion for subsequent semantic call-graph work.

- it is the compile metadata for the workspace's real Windows build;
- clangd resolved the representative RSS2-local, Wiremod-local, and Unreal symbols successfully from it;

The Clang-derived database remains useful as a comparison/fallback if later semantic behavior differs.

The earlier `ParallelFor` diagnostic in `RSSDataManagerSubsystem.cpp` remains a localized source/parse issue worth remembering, but it is not a B2 blocker: other non-trivial RSS2 and Wiremod translation units resolve project/dependency symbols correctly, and the diagnostic was identical under both compiler views.

## 1.6 B3 method — prove semantic call hierarchy

**Status: passed on the configured Windows UE 5.6.1-CSS / SML workspace (2026-09-24).**

B3 uses clangd's LSP call-hierarchy interface directly:

```text
textDocument/prepareCallHierarchy
callHierarchy/incomingCalls
callHierarchy/outgoingCalls
```

The probe deliberately targets an ordinary RSS2 C++ function whose direct call edges span several source files:

```text
URssBlueprintFunctionLibrary::IsSignDataSafe(const FRssSignData&)
```

Pinned source establishes useful manual expectations before the semantic query runs.

Known incoming call sites include:

```text
RSSSignRCO.cpp
  RCO_Server_UpdateSignData_Validate(...)
  RCO_MultiCast_ApplySignData_Validate(...)

RSSTemplateSubsystem.cpp
  RCO_AddTemplate_Implementation(...)
  RCO_AddTemplate_Validate(...)

RssJsonSerializer.cpp
  JsonToSignData(...)
  JsonToTemplates(...)
  StructToJson(...)
```

A known cross-file outgoing edge is:

```text
IsSignDataSafe(...)
  -> URssDownloadImage::IsStructurallySafeRemoteImageUrl(...)
     [RssDownloadImage.h / RssDownloadImage.cpp]
```

To keep project-wide indexing focused, the B3 probe creates an ignored derivative compilation database containing only the RSS2 translation units from the proven B1 MSVC-derived database. No compiler flags, response-file arguments, or source are reconstructed.

Run:

```powershell
python .\playground\external-call-map\b3_probe_call_hierarchy.py
```

The probe starts clangd with background indexing against that filtered database, prepares the call-hierarchy item semantically, then queries incoming and outgoing calls until enough known cross-file coverage is available or the timeout expires. Returned call-site ranges are also mapped back to source lines for human verification; the edges themselves come only from clangd, not from source-text parsing.

### 1.6.1 First configured run: clangd 19 is insufficient

The first Windows run used the Visual Studio-bundled clangd 19.1.5.

It successfully prepared the semantic root item for `URssBlueprintFunctionLibrary::IsSignDataSafe`, but:

- `callHierarchy/outgoingCalls` returned LSP error `-32601 method not found`;
- `callHierarchy/incomingCalls` returned no callers during the five-minute probe window;
- the first probe recorded 60 progress events but did not retain their payloads, so that run cannot prove whether background indexing had actually completed before the timeout.

This is a tooling-version limitation, not evidence that the RSS2 call graph is unavailable. Direct inspection of the matching LLVM source confirms that clangd 19.1.5 binds `prepareCallHierarchy` and `incomingCalls` but has no outgoing-call implementation. clangd 20.1.0 adds `outgoingCalls` and the extra index support required for outgoing-call containment.

The revised B3 probe therefore:

- requires clangd 20 or newer before doing expensive indexing;
- keeps the B1 MSVC-derived build metadata unchanged;
- uses a clangd-major-specific ignored index directory so clangd 19 shards cannot contaminate a newer outgoing-call-capable run;
- records the actual `backgroundIndexProgress` payloads and recognizes explicit indexing completion before judging missing incoming edges;
- increases the safety timeout to 15 minutes while still stopping shortly after a completed index if the expected edges remain absent.

A newer standalone clangd may be supplied explicitly:

```powershell
python .\playground\external-call-map\b3_probe_call_hierarchy.py --clangd "C:\path\to\clangd.exe"
```

Generated state remains under:

```text
work/external-call-map/b3/
├─ rss-compile-db-clangd-<major>/
│  ├─ compile_commands.json
│  └─ .cache/clangd/index/...
├─ b3-call-hierarchy-summary.json
└─ clangd-<major>-call-hierarchy-stderr.log
```

### 1.6.2 clangd 22 + MSVC-derived database result

The next configured Windows run used standalone clangd 22.1.8 against the RSS2-only derivative of the real B1 MSVC-derived database.

That run established:

- `prepareCallHierarchy`, `incomingCalls`, and `outgoingCalls` were all implemented and returned without LSP errors;
- background indexing explicitly reached `backgroundIndexProgress: { "kind": "end" }`;
- outgoing hierarchy from `IsSignDataSafe` resolved same-file helper calls and Unreal Engine calls such as `FString::Len` / `FText::ToString`;
- no incoming calls were returned;
- the known cross-file outgoing edge to `URssDownloadImage::IsStructurallySafeRemoteImageUrl` was absent.

The result therefore proves the clangd-19 method gap is fixed but does **not** yet prove that project-wide cross-translation-unit reference data from the MSVC-derived database is usable for call hierarchy.

The next B3 experiment compares the background-index behavior of the two UBT compiler views already validated in B2. The probe now defaults to the B2 Clang-derived database:

```powershell
python .\playground\external-call-map\b3_probe_call_hierarchy.py
```

To reproduce the MSVC-derived view explicitly:

```powershell

```

The two views use separate ignored clangd index caches. The summary also records counts/samples for successful `Indexed ...` log lines, `Failed to compile ...` lines, and hard `Indexing ... failed:` lines so a drained queue is no longer treated as proof that every translation unit indexed cleanly.

### 1.6.4 Focused clangd 22 compile diagnostics

The foreground diagnostic probe reproduced a common first hard diagnostic in all three representative RSS2 translation units:

```text
[builtin_definition] ... definition of builtin function '_m_prefetch'
[fatal_too_many_errors] ... too many errors emitted, stopping now
```

`RssBlueprintFunctionLibrary.cpp` emitted additional downstream diagnostics after the builtin conflict, but `RssJsonSerializer.cpp` and `RssDownloadImage.cpp` both stopped on the same `_m_prefetch` conflict plus the fatal error cap. This makes the builtin conflict the current first common incompatibility to isolate.

The earlier background-index log showed that the UBT Clang response files explicitly carry a Clang-19 resource directory while the analysis frontend is clangd 22. LLVM changed `_m_prefetch` / `_m_prefetchw` handling in newer Clang versions from header-provided definitions to compiler builtins to avoid Windows header conflicts. A clangd-22 frontend consuming Clang-19 resource headers is therefore a concrete version-skew candidate for this exact error.

The next B3 experiment changes **only** that variable. It copies the response files for the same three representative TUs into ignored `work/` state, removes their explicit `-resource-dir=.../clang/19` token, and leaves the compiler argv[0] plus every other UBT flag unchanged:

```powershell
python .\playground\external-call-map\b3_probe_resource_dir_alignment.py
```

clangd will then be free to inject its own matching resource directory. The probe records the effective resource directory seen by clangd and whether the common `_m_prefetch` failure disappears.

### 1.6.6 clangd 22 remaining-error result and version pivot

The configured Windows run raised the aligned response-file error cap to 100.

All three representative translation units still exhausted that limit. `RssJsonSerializer.cpp` and `RssDownloadImage.cpp` exposed no useful source diagnostic before `fatal_too_many_errors`; `RssBlueprintFunctionLibrary.cpp` exposed only a few downstream semantic errors in addition to the same fatal cap.

Continuing to raise the clangd-22 error limit would therefore mix B3 with a broad Clang-22-vs-UE/UBT compatibility investigation.

There is a narrower version experiment available.

LLVM source establishes that clangd 20.1.8 already implements:

```text
textDocument/prepareCallHierarchy
callHierarchy/incomingCalls
callHierarchy/outgoingCalls
```

while the newer X86 builtin definition for `_m_prefetch` / `_m_prefetchw` is absent from LLVM 20.1.8 and present by LLVM 21.1.1. clangd 20 is therefore a materially closer frontend to the UBT/Visual-Studio Clang-19 toolchain while still satisfying B3's bidirectional call-hierarchy requirement.

The next B3 experiment should use an **unmodified** B2 Clang-derived database with standalone clangd 20.1.8.


Use the official LLVM 20.1.8 Windows x64 installer from the upstream release and do not add/replace the global PATH entry if the installer offers that choice.

Then run:

```powershell
python .\playground\external-call-map\b3_probe_call_hierarchy.py \
  --clangd "C:\Program Files\LLVM-20.1.8\bin\clangd.exe" \
```

#### clangd call-range URI limitation

The first B4 result also exposed a presentation limitation in clangd 20's outgoing call-hierarchy API.

The B4 script now avoids claiming such a mapping unless the caller item URI itself is a C/C++ source translation unit. Otherwise it records:

```text
source_line_mapping.status =
  unmapped-caller-item-is-canonical-declaration
```

and leaves `source_lines` empty. It also deduplicates identical call ranges returned by the index.

This does not change edge discovery or traversal; it prevents a human-readable evidence field from overstating what the LSP result actually identifies.

### 1.9.1 Semantic proof chain

B6 does not search source text for `override`, lifecycle names, or declaration syntax.

For each RSS2 header, clangd provides hierarchical `textDocument/documentSymbol` results. For each class-like symbol with methods:

```text

  -> textDocument/prepareTypeHierarchy
  -> typeHierarchy/supertypes
  -> external ancestor classes
```

A same-name match alone is **not** sufficient. For every external base-method candidate, the probe asks:

```text

```

and accepts the RSS2 method as an external override only if clangd returns that RSS2 method's declaration/definition location as an implementation of the external method.

The resulting evidence chain is therefore:

```text
RSS2 method declaration
  -> semantic RSS2 class hierarchy
  -> external ancestor
  -> indexed external base method
  -> clangd override/implementation relation
  -> RSS2 method location
```

This uses Clang/clangd's own AST and index relations rather than implementing a C++ parser or matching `override` tokens.

- RSS2 declaration location;
- RSS2 definition location(s) when clangd resolves them;

- external base-method declaration location;
- the RSS2 implementation location returned by clangd;

No generic external override is silently promoted to a final entry-point classification.


The first important B7 family beyond generic overrides is **Unreal dynamic-delegate handlers**.

### 1.10.1 Dynamic-delegate proof

Current RSS2 contains 13 real `AddDynamic` registrations across three C++ source files, representing 11 unique callback methods.

Representative shape:

```cpp
SomeDelegate.AddDynamic(this, &ThisClass::Handler);
```

The B7 probe is:

```text
research/external-call-map-feasibility/b7_probe_dynamic_delegate_bindings.py
```

with evaluation-only controls in:

```text
research/external-call-map-feasibility/b7_delegate_controls.json
```

The discovery rule is deliberately narrow rather than pretending to parse arbitrary C++:

```text
.AddDynamic(receiver, &QualifiedClass::Handler)
```

A textual match is only a **registration candidate**. The handler becomes a B7 callback-root candidate only after clangd `textDocument/definition` on the member-function token resolves back to an RSS2 declaration.

For each registration, the probe records:

- registration file, source line, and exact source range;
- enclosing function/method from clangd document symbols;
- qualified handler spelling from the registration;
- semantic handler declaration/definition locations;
- any clangd definition for the `AddDynamic` macro token;
- focused foreground-AST evidence from the registration line;
- whether the resolved handler belongs to RSS2.

Repeated registrations are merged into one handler-root record with multiple registration sites.

This gives both halves required for a useful call-map root:

```text
where callback becomes registered
        +
which project method Unreal may invoke later
```

It does **not** claim the registration path necessarily executes in every runtime configuration. Registration reachability and delegate broadcast behavior remain separate graph questions.

### 1.10.5 Why UHT families are different

Unreal reflection macros such as:

```text
UFUNCTION(...)
UPROPERTY(...)
```

are consumed by UnrealHeaderTool. From the ordinary C++ compiler's perspective they are intentionally ignored/empty annotation macros.

That means clangd can semantically understand the resulting C++ declarations, but its normal AST does not inherently retain facts such as:

```text
this function is Server Reliable
this property uses OnRep_SignDataDirty
this event is BlueprintImplementableEvent
```

Those are UHT/reflection facts rather than ordinary C++ virtual-dispatch facts.

RSS2 contains concrete examples of each:

```text
URSSTemplateSubsystemRCO::RCO_*         -> Server RPC declarations
RequestCustomSignMulticast             -> NetMulticast RPC
OnRep_SignDataDirty                    -> ReplicatedUsing callback
URssSignWidget::OnBuildableSet         -> BlueprintImplementableEvent
URssSignWidget::OnRequestUpdateSign    -> BlueprintNativeEvent
```

A future analyzer can add small explicit macro-token rules or consume generated/UHT metadata for these families. B7 does not treat a source macro spelling alone as equivalent to a compiler-semantic proof of runtime dispatch.

For Blueprint events there is an additional blind spot: even recognizing the reflected event declaration does not prove that a particular Blueprint asset implements it or where that Blueprint graph executes. That requires asset/generated-class information beyond the current C++-only semantic layer.

### 1.10.7 B7 conclusion

**B7 passes.**

The experiment establishes that the future root-discovery layer does not need one universal mechanism. A thin family-specific rule layer is sufficient:

```text
virtual/framework overrides
  -> B6 semantic override discovery
  -> framework label enrichment

explicit callback registration
  -> small registration-shape rule
  -> semantic target resolution
  -> dynamic delegates proven in B7

UHT/reflection dispatch
  -> explicit UHT/generated metadata layer
  -> RPC / RepNotify / Blueprint annotations

asset/generated-class dispatch
  -> asset or generated-class layer
  -> Blueprint implementation visibility
```

Supported/reasonable families after B7:

| Family | Evidence/approach after B7 |
| --- | --- |
| Unreal module lifecycle | B6 external override + small framework rule |
| Actor/component lifecycle | B6 external override + engine base/method rule |
| SML Mod Module lifecycle | Same override enrichment when a concrete project override exists; RSS2 lacks a direct specimen |
| SML `AModSubsystem` lifecycle | Semantic ancestry/override enrichment is available; framework instantiation itself still needs SML-specific knowledge |
| Unreal dynamic delegates | **Proven:** registration rule + semantic callback resolution |
| SML native hooks | Same registration-rule architecture appears appropriate, but RSS2 contains no `SUBSCRIBE_METHOD*` specimen, so this remains unvalidated |
| RPC / NetMulticast | Requires UHT/generated reflection metadata or explicit annotation parsing; plain C++ AST is insufficient |
| RepNotify / `OnRep` | Requires UHT/generated reflection metadata or explicit `ReplicatedUsing` rule |
| BlueprintImplementableEvent / BlueprintNativeEvent | Declaration can be recognized from UHT metadata; actual Blueprint implementation requires asset/generated-class data |
| Blueprint/SML Blueprint hooks | Requires asset/generated-class/hook-registration information beyond the current C++ semantic layer |

The unsupported families are therefore understood **blind spots with identifiable evidence layers**, not evidence that the semantic call-map foundation is blocked.

## 1.11 B8 feasibility decision

**Status: completed on the configured Windows UE 5.6.1-CSS / SML workspace (2026-09-24).**

**Decision: viable with known blind spots.**

A useful External Call Map **should be buildable** from the existing UnrealBuildTool project view, clangd/Clang semantic queries, a thin framework-entry rule layer, and a bounded graph/navigation layer.

BX found no evidence that this requires either:

```text
a bespoke C++ parser
or
deep semantic coupling to Rider/ReSharper internals
```

Rider remains a reasonable eventual host for the user interface, but it does not need to own the semantic truth.

### 1.11.1 Evidence behind the decision

| Task | Established fact | B8 significance |
| --- | --- | --- |
| **B1** | UBT produced real `FactoryEditor / Win64 / Development` compile metadata with 2,175 translation units, including 28 RSS2 and 193 Wiremod entries. | The analyzer can start from the build system's actual include/define/response-file knowledge instead of reconstructing Unreal compilation rules. |
| **B2** | clangd resolved representative RSS2-local, Wiremod-local, and Unreal Engine symbols against UBT-owned compile views. | Existing semantic machinery understands the configured project well enough to reuse rather than replace. |
| **B3** | clangd 20.1.8 returned correct project-local outgoing call edges across source-file boundaries with semantic source locations. | Ordinary C++ call-graph edges are available without source-text parsing. |
| **B4** | A manual Unreal lifecycle root produced a stable multi-level RSS2 graph with 19 nodes, 18 project edges, cross-file traversal, bounded expansion, and manually verified edges. | A rooted project call map is not merely theoretical. |
| **B5** | Five roots produced a 108-node / 162-edge merged RSS2 graph; cycles and overlap were handled, and no traversal hit the node cap. | Project-scale traversal is operationally tractable, but the presentation must be lazy, filtered, and cached. |
| **B6** | Reverse-index discovery produced 40 external-override candidates; foreground Clang AST recovered demonstrated reverse-index misses and rejected an ordinary local negative. | External virtual/framework roots can be discovered semantically without regex or a custom parser. |
| **B7** | All 13 current RSS2 `AddDynamic` registrations resolved semantically to 11 callback methods, with zero unresolved registrations. | Important non-override framework roots can be added through small registration-specific rules plus semantic target resolution. |

Together these satisfy the original BX definition of "possible": representative translation units can be understood, ordinary cross-file call edges exist, bounded rooted graphs work, useful roots can be inferred automatically, and the remaining unsupported families have identifiable enrichment layers rather than a fundamental semantic blocker.

### 1.11.2 Ownership of future work

| Layer | Owns | Should not own |
| --- | --- | --- |
| **UBT / compile metadata** | Target/configuration selection, translation-unit commands, include paths, defines, generated-header paths, response-file knowledge. | Call-graph interpretation or framework-root classification. |
| **clangd / Clang semantic layer** | Symbols, definitions, call edges, type hierarchy, foreground AST facts, authoritative override relationships for opened declarations. | Unreal/SML product policy such as which valid override is worth showing as a root. |
| **Entry-point rule layer** | Framework meaning: lifecycle labels, external-override candidate filtering, delegate registrations, future SML-hook rules, and adapters for UHT/generated metadata. | General C++ parsing or recursive graph traversal. |
| **Graph layer** | Project-boundary filtering, node identity, deduplication, cycle handling, root unioning, caching, confidence/provenance metadata, lazy/depth-limited traversal. | Compiler semantics or UI-specific rendering. |
| **Eventual Rider UI** | Navigation, expand/collapse, filtering, root confirmation/suppression, progress/background presentation, and editor jumps. | Being the only source of semantic truth or requiring deep ReSharper internals for correctness. |

The preferred dependency direction is therefore:

```text
UBT compile truth
  -> clangd / Clang semantic service
     -> framework-entry adapters
        -> bounded cached graph
           -> Rider UI
```

The semantic service and graph model should remain usable outside Rider. A future Rider plugin can host/control them, but the experiment provides no reason to make Rider APIs the foundation of call discovery.

### 1.11.3 Known blind spots and required mitigations

| Blind spot | Evidence from BX | Required stance |
| --- | --- | --- |
| **Incomplete clangd background index coverage** | B3-B6 repeatedly saw all 28 RSS2 TUs marked as potentially incomplete; incoming calls remained empty and reverse override discovery had real false negatives. | Do not claim whole-program completeness. Prefer forward/outgoing traversal, preserve confidence/provenance, and use foreground AST checks where correctness matters. |
| **clangd/toolchain version sensitivity** | clangd 19 lacked outgoing-call support; clangd 22 was incompatible with the tested Clang-19-flavored UE workspace; clangd 20.1.8 worked. | Pin/test the semantic backend version against the configured UE/SML toolchain instead of assuming newest-is-best. |
| **Outgoing call-site URI ambiguity** | clangd 20 can return implementation `fromRanges` while canonicalizing the caller item to a header declaration. | Treat the semantic edge as valid but do not invent a source URI for a range the protocol did not identify. |
| **UHT/reflection dispatch** | RPC, NetMulticast, RepNotify, and Blueprint-event semantics are not fully represented by the ordinary C++ AST. | Add explicit UHT/generated-metadata adapters; do not fake these relations from ordinary call hierarchy. |
| **Blueprint implementation graphs** | C++ can identify reflected declarations, but actual Blueprint implementations and graph execution require asset/generated-class information. | Keep deep Blueprint reconstruction as a separate enrichment layer, not a prerequisite for the C++ call map. |
| **SML native hooks** | The analogous registration-rule architecture is plausible, but RSS2 contains no real `SUBSCRIBE_METHOD*` specimen. | Validate on a real project specimen before claiming support. |
| **Wiremod graph traversal depth/scale** | B1/B2 proved Wiremod compile metadata and semantic symbol resolution, while B3-B7 deliberately used RSS2 for the deep graph experiments. | Treat RSS2 as the proven traversal specimen; perform a focused Wiremod validation when productization begins rather than assuming identical edge coverage. |
| **Current probe performance** | B5's deliberately eager cold five-root experiment took 340 s; B7's focused foreground run took about 32 s. | Use a persistent semantic process/index, cache results, query lazily, default to shallow project-only expansion, and hide boundary noise until requested. |

These limitations justify **viable with known blind spots** rather than an unqualified "viable" verdict. None currently requires replacing the semantic foundation.

### 1.11.4 Product boundary implied by BX

The first useful product should be C++-semantic-first rather than a promise of perfect Unreal runtime reconstruction.

Its credible core is:

```text
discover external/framework root candidates
  -> show provenance/confidence
  -> traverse project-local outgoing semantic edges
  -> expand lazily
  -> deduplicate shared nodes
  -> mark cycles
  -> hide external/engine noise by default
  -> allow framework adapters to contribute extra roots
```

A root or edge should be able to say **why** it exists, for example:

```text
manual-confirmed
semantic external override
foreground-AST override proof
Unreal AddDynamic registration
future UHT/reflection metadata
future SML hook registration
```

That keeps established semantic facts separate from framework-specific inference and from unsupported runtime behavior.

### 1.11.5 Go / no-go

**Go.**

The semantic foundation is good enough to justify post-BX product/design work.

The next phase should **not** begin by writing a polished Rider graph window. The sensible order is to stabilize a persistent analyzer/graph interface around the proven UBT + clangd/Clang stack, then add the Rider presentation layer on top. UHT/SML/Blueprint enrichments can be added as explicit adapters without changing the core graph model.

BX stops here. The experiment has answered its feasibility question; the deferred productization work below is now technically justified, but remains outside BX and outside the current implementation freeze unless explicitly authorized.
