# FL-B170 — Add a headless developer CLI/integration harness

## State

`QUEUED`

Dependencies: `FL-B150`, `FL-B160`

## Description

Provide a cohesive supported developer-facing headless path that exercises the analyzer without Rider.

This is **not** a greenfield CLI task. Several task-specific commands already exist and should be reused/refactored where appropriate rather than duplicated.

## Existing baseline to build on

The current CLI already contains narrow supported development/validation commands including:

```text
compile-metadata
backend-check
call-expand-check
external-override-check
```

Those commands were introduced to validate B100/B110/B130/B150 surfaces individually. They are useful implementation pieces and evidence, but they do not yet satisfy B170's cohesive analyzer-level integration contract by themselves.

B170 should compose the supported workspace/backend/root/graph APIs into one intentional headless workflow instead of teaching CLI presentation code its own semantic rules.

## Requirements

- Initialize a supported analyzer session for a configured workspace/target.
- Discover/list roots from the supported root providers available after B150/B160.
- Select a discovered root without relying on unstable display-only identity.
- Expand a selected root through supported graph/call APIs.
- Exercise bounded/cached graph behavior rather than bypassing FL-B140 with bespoke recursion.
- Emit useful human-readable output.
- Provide a machine-readable result form suitable for integration validation.
- Preserve root/edge evidence and completeness/diagnostic information in the output surface.
- Surface configuration/backend/query failures honestly.
- Reuse existing task-specific commands/helpers where they genuinely reduce duplication, while keeping their narrow validation roles distinguishable from the general integration command.

## Constraints / non-goals

- This is a development/test surface, not necessarily a promised end-user CLI product.
- Do not duplicate semantic logic in CLI presentation code.
- Do not turn the CLI into a second analyzer architecture or a substitute for the Rider frontend.
- Do not delete narrow task-specific validation commands merely for aesthetic consolidation if they remain useful reproducible acceptance tools.

## Acceptance criteria

A supported command can initialize the analyzer, list supported roots, select one by stable identity, expand it through supported graph APIs, and emit both human-readable and machine-readable results without Rider.

## Validation

- Exercise the cohesive CLI path against controlled fixtures.
- Exercise it against at least one configured real workspace.
- Verify the machine-readable form is deterministic enough for later FL-B190 integration validation.
- Keep existing expensive Windows/environment-specific checks separate where appropriate rather than making every small CLI test require a real Satisfactory workspace.
